02 · 從使用者程式進入核心 ​

使用者程式要讀檔時，會呼叫 read()，把檔案描述符、緩衝區位址和長度交給核心。它在 U-modeRISC-V 的權限層級。U-mode 跑使用者程式，只能依核心設定存取資源。WUWAOS 核心跑在 S-mode，負責頁表、陷阱和硬體服務。 執行 ecall 後，CPU 轉入核心使用的 S-mode。這次受控的交接稱為系統呼叫使用者程式請核心代辦工作的介面。例如 read() 透過 ecall 把編號和參數交給核心，完成後取得讀了幾個 bytes 或錯誤碼。。

為什麼需要由核心接手 ​

一般函式呼叫在同一個權限層級內跳到另一段程式。讀檔需要查行程的資源、驗證使用者指標，還可能操作裝置。這些工作由核心負責。使用者端函式會先把參數放到雙方約定的暫存器，再用 ecall 請 CPU 轉入核心。這份「哪個暫存器放什麼、結果如何回來」的約定可從 WUWAOS 的使用者函式庫和分派器兩端對照。 使用者 API · 系統呼叫分派

CPU 也可能因為別的原因進入同一條陷阱入口。執行指令本身引發的事件是同步例外，例如 ecall 或缺頁。裝置和計時器則可在指令流進行時提出非同步中斷。三者都會保存續跑需要的狀態，核心再依事由決定怎麼處理。

系統呼叫如何往返 ​

  1. 使用者函式庫依約定放入參數。前三個參數用 a0 至 a2，呼叫編號用 a7。
  2. ecall 觸發陷阱CPU 暫停目前指令流程，跳到核心的事件處理入口。原因可能是程式主動呼叫核心、執行指令時遇到例外，或硬體發出的計時器／裝置中斷。。CPU 進入由 stvec 指定的共同入口，核心組合語言切換堆疊，將暫存器保存到 TrapFrame陷阱發生時由核心保存的一組暫存器與返回位置。核心返回使用者模式之前，會依它還原需要的狀態。。
  3. trap_handler() 依 scause 判斷原因。系統呼叫交給 syscall_dispatch()，一般回傳值寫回 a0。需讀寫使用者資料的路徑會檢查位址和權限。
  4. 若需要等磁碟或 Pipe，呼叫者可停在原本的核心函式內，由排程器換另一條 Thread。原 Thread 回來後接續未完成的呼叫。
  5. 正常完成時，核心還原使用者狀態，以 sret 返回。

進入核心後從哪裡繼續 ​

事件核心做什麼返回位置
使用者 ecall呼叫 syscall_dispatch()。一般前進 4 bytes 越過 ecall。成功的 exec() 改從新程式入口開始，exit() 結束行程。
取指、讀取或寫入缺頁vm_handle_fault() 用 stval 找到相關位址，檢查原始權限並補頁。成功時以原 sepc 重試。非法存取或無法補頁時會結束行程。
計時器或外部中斷時間片到期可換 Thread，外部中斷交給裝置處理。原 Thread 恢復時從保存的 sepc 繼續。

scause 表示為什麼進核心，sepc 表示返回或重試的位置，stval 在缺頁時提供相關虛擬位址。傳入的 user buffer 只是一個待驗證的位址。對應到頁框後，寫入還可能觸發寫入時複製。

TrapFrame 和核心上下文各保存一次什麼 ​

以阻塞的 read() 為例，第一次保存發生在由使用者態進入核心時。TrapFrame 留下程式的暫存器和返回位置。第二次發生在核心的讀取函式等待資料時。排程器保存讓這條執行緒回到同一段核心呼叫所需的暫存器與堆疊位置。醒來後先回到核心函式，等到讀取有結果，才把回傳值寫回 TrapFrame，最後以 sret 回到使用者程式。 陷阱組語 · 上下文切換
