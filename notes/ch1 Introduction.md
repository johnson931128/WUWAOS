## User View 與 System View 的架構哲學

在探討作業系統時，課本提出了一個極度精闢的比喻：「**作業系統就像政府 (Similar to a government)**」。政府本身不會製造實體產品（不執行使用者的業務邏輯），但它制定法律、修建高速公路（提供資源與環境），讓百業（應用程式）得以繁榮。要理解這個「政府」，必須從兩種截然不同的角度來觀察：

### 1. 1.1.1 User View (使用者觀點)：極致的自私與便利
使用者的觀點，完全取決於當下使用的「介面 (Interface)」與「硬體型態」。

* **PC 與筆記型電腦 (Monopolized Resources)**：
    當一個人坐在電腦前打遊戲或寫程式時，目標只有一個：**將工作或娛樂的效能最大化**。在這種情境下，作業系統的設計哲學是追求絕對的 **「易用性 (Ease of use)」**。
    
    系統被設計成讓單一使用者「壟斷 (Monopolize)」所有資源。此時的 OS **完全不在乎「資源利用率 (Resource utilization)」**——就算 CPU 有 99% 的時間在發呆等鍵盤輸入，只要滑鼠動起來不卡頓，這就是一個好系統。
* **行動裝置 (Mobile Devices)**：
    視角轉移到手機或平板，使用者介面變成了觸控螢幕 (Touch screen) 與語音辨識 (Voice recognition，如 Siri)。此時 OS 的重點轉向了手勢的流暢度與感測器的即時回饋。
    
* **嵌入式系統 (Embedded Computers)**：
    例如汽車引擎控制電腦或微波爐。在這種環境下，使用者觀點**幾乎徹底消失 (Little or no user view)**。系統被設計為在沒有任何人為干預的情況下，日復一日地死板運行。

### 2. 1.1.2 System View (系統觀點)：上帝視角與勞碌的總管
如果把眼睛貼在實體主機板上，從硬體的角度往上看，作業系統是與硬體交涉最深的終極核心。它肩負著兩大神聖使命：

* **使命一：資源分配者 (Resource Allocator)**
    CPU 時間、記憶體空間、硬碟、網路卡，這些都是極度稀缺的物理資源。面對成百上千個同時發出請求的應用程式，OS 必須站出來當裁判，決定誰先用、誰後用。這正是我們在 Chapter 5 學了整整一章「CPU Scheduling」的最底層初衷——**在充滿衝突的請求中，達成系統的高效與公平 (Efficiently and fairly)**。
    
* **使命二：控制程式 (Control Program)**
    軟體工程師寫出來的程式往往充滿 Bug，甚至帶有惡意。OS 必須像防暴警察一樣，管理所有 User Programs 的執行，**防止錯誤發生 (Prevent errors)** 以及**防止電腦被不當使用 (Improper use)**。例如：絕對不允許一個普通的 C++ 程式直接繞過 OS 去操控實體硬碟的讀寫頭，所有的 I/O 動作都必須經過 OS 的嚴格審查。

## 作業系統定義與軟體架構層次剖析

這段內容探討了作業系統的本質與邊界。隨著硬體的演進，釐清哪些程式碼屬於 OS、哪些屬於應用程式，成為了系統架構的必考觀念。

### 1. 歷史驅動力與摩爾定律
電腦的發展從軍事密碼破解等 **Fixed-purpose systems (特定用途系統)**，逐漸演化為具備多功能的 **General-purpose (通用型)** 主機，作業系統也因此誕生。
推動這一切的底層物理法則是 **Moore's Law (摩爾定律)**：預測積體電路上的電晶體數量每 18 個月會翻倍。這項定律促成了硬體體積微縮與算力暴增，使得 OS 能夠被塞進從太空船到烤麵包機等各式各樣的設備中。

### 2. 作業系統的誕生初衷
電腦系統的根本目標是「執行程式並解決使用者的問題」。由於 **Bare hardware (裸機硬體)** 極度難以直接操控，軟體工程師開發了 **Application programs (應用程式)**。
然而，所有的程式都需要控制 I/O 設備、申請記憶體。將這些「共通功能 (Common functions)」抽離出來，集中到單一的軟體層中進行資源分配與控制，這個軟體層就是作業系統。


### 3. 🚨 考試絕對重點：如何定義 OS 的邊界？
針對「什麼是作業系統」，實務與學術上有不同的解讀層次，必須精準掌握以下專有名詞：

* **供應商觀點 (Vendor's View)**：
  買 OS 時附贈的所有東西（包含圖形介面、瀏覽器等）。這曾引發 1998 年美國司法部控告微軟的反托拉斯案 (Antitrust suit)，微軟被控藉由將網頁瀏覽器綑綁進 OS 中來壟斷市場。
  
* **學術/核心定義 (The Standard Definition)**：
  這是考試最常考的標準定義。作業系統是指 **「在電腦上隨時保持執行狀態的那一個唯一程式 (The one program running at all times on the computer)」**，這個程式被專稱為 **Kernel (核心)**。
* **非核心程式的分類**：
  伴隨 Kernel 運行的其他程式，被嚴格劃分為兩類：
  1. **System programs (系統程式)**：與 OS 運作密切相關，但不屬於 Kernel 內部程式碼（例如：背景系統日誌收集器）。
  2. **Application programs (應用程式)**：與系統底層運作無關的純使用者程式（例如：Web 瀏覽器、文字編輯器）。

### 4. 現代系統的架構擴充：中介軟體
隨著智慧型手機的普及，現代 Mobile OS（如 Apple's iOS 與 Google's Android）的定義範圍再次擴大。除了底層的 Core kernel，它們還包含了 **Middleware (中介軟體)**。這是一組龐大的軟體框架 (Software frameworks)，專門提供資料庫存取、多媒體渲染等額外服務給開發者，大幅降低了開發手機 App 的門檻。

## 儲存結構理論與物理階層剖析

#### 1. 運算的唯一舞台：Main Memory (主記憶體)
從硬體架構的絕對規則來看，**CPU 是一頭被蒙住眼睛的猛獸，它唯一能直接「吃」到的指令與資料，全部來自 Main Memory**。
* **RAM (Random-Access Memory)**：現代通用電腦的主記憶體幾乎都採用 DRAM (動態隨機存取記憶體) 技術。它是系統執行應用程式的絕對核心。
* **揮發性 (Volatile) 的致命傷**：RAM 只要一斷電，內部資料就會瞬間灰飛煙滅。
* **Bootstrap Program (啟動程式)**：既然 RAM 斷電會清空，電腦剛通電時，CPU 該去哪裡找第一行指令碼？答案是 **EEPROM** (電子抹除式可複寫唯讀記憶體) 或其他形式的 **Firmware (韌體)**。這些儲存載體速度較慢，但具備**非揮發性 (Nonvolatile)**，負責在開機瞬間喚醒系統並載入作業系統核心。

#### 2. Von Neumann 架構下的資料流動
在經典的馮·紐曼架構中，CPU 與記憶體之間的互動極度單純，僅透過兩種基本指令：
* **`load` (載入)**：將資料從主記憶體搬移到 CPU 內部的暫存器 (Register)。
* **`store` (儲存)**：將 CPU 算好的結果，從暫存器倒回主記憶體中。
* **底層視角**：對主記憶體而言，它根本不知道自己儲存的是 C++ 程式碼、高畫質圖片還是 ROS 2 的控制訊號。它只會看到一連串冰冷的「記憶體位址 (Memory addresses)」不斷湧入。

#### 3. 物理的殘酷妥協：Storage-Device Hierarchy (儲存裝置階層)
由於無法打造出「容量無限大、速度無限快且永不掉電」的記憶體，硬體架構師建構了一座階層分明的金字塔 (如課本 Figure 1.6 所示)。這座金字塔越往上，速度越快、造價越昂貴、容量越小。
![image](https://hackmd.io/_uploads/r1sTm8SnWe.png)
* **Primary Storage (主要儲存)**：包含 Registers (暫存器)、Cache (快取)、Main Memory。由半導體 (Semiconductor) 打造，速度極快但皆為**揮發性 (Volatile)**。
* **Secondary Storage (次要儲存)**：做為主記憶體的延伸，負責永久保存海量資料。包含 HDD (硬碟) 與 NVM (非揮發性記憶體，如 SSD)。
* **Tertiary Storage (第三級儲存)**：如 Optical disk (光碟)、Magnetic tapes (磁帶)。速度極慢，專門用來做冷資料的災難備份。

#### 4. 🚨 專有名詞與現代儲存分類 (Terminology)
作業系統工程師必須精確使用以下專有名詞：
* **Memory (記憶體)**：在系統語境中，單指「揮發性」的儲存空間 (Volatile storage)。
* **NVS (Nonvolatile Storage / 非揮發性儲存)**：斷電後資料依然存在的空間。NVS 在現代硬體中爆發出兩大陣營的對決：
    * **Mechanical (機械式)**：如傳統 HDD。依靠馬達與磁頭進行物理讀寫。優勢是「每位元組成本極低、容量巨大」，劣勢是物理極限導致的存取延遲。
    * **Electrical (電子式)**：如 Flash memory (快閃記憶體)、SSD (固態硬碟)。統稱為 **NVM (Nonvolatile Memory)**。完全沒有活動式機械零件，速度遠超機械硬碟，但造價昂貴且容量有物理極限。

---
**【重點摘要】**
* **硬體名詞辨析**：嚴格區分了 Processor（實體晶片）與 Core（運算核心）的物理邊界。
* **SMP (對稱式多處理)**：現代電腦的標準架構，所有核心地位平等、共享主記憶體，但面臨「匯流排競爭」的物理擴充極限。
* **Multicore (多核心優勢)**：相比於多顆單核晶片，將多個核心封裝在同一實體晶片內，具備通訊速度快且**功耗極低 (Power efficiency)** 的絕對優勢。
* **NUMA (非均勻記憶體存取)**：為突破 SMP 的匯流排瓶頸而生，將記憶體區域化 (Local memory)，帶來了極高的整體頻寬，但也引發了跨區存取的延遲懲罰 (NUMA Penalty)。

## 多處理器架構與名詞深度解析

### 1. 嚴格的硬體名詞定義 (Definitions of Components)
在討論多處理器系統前，作業系統工程師必須精確定義以下五個極易混淆的名詞（參考課本的藍色定義框）：
* **CPU (中央處理器)**：負責執行指令的硬體總稱。在現代語境中，常作為單一運算單元的泛稱。
* **Processor (處理器)**：指那塊肉眼可見、插在主機板上的 **「實體晶片 (Physical chip)」**。一顆 Processor 內部可以包含一個或多個 CPU。
* **Core (核心)**：CPU 內部的 **「基本運算單元 (Basic computation unit)」**。
* **Multicore (多核心)**：在「同一顆」實體晶片 (Processor) 上，封裝了多個運算核心。
* **Multiprocessor (多處理器)**：整個電腦系統內，插了「多顆」實體處理器晶片。

### 2. 吞吐量的假象與 SMP 架構 (Symmetric Multiprocessing)
![image](https://hackmd.io/_uploads/H1zGw8ShWx.png)
增加運算核心的主要目的是為了提升**吞吐量 (Throughput)**。但課本提出了一個殘酷的數學現實：**「$N$ 顆處理器的加速比 (Speed-up ratio) 絕對小於 $N$」**。
這是因為系統需要付出維持資料同步的**純耗損 (Overhead)**，以及對共享資源的**競爭 (Contention)**。

目前統治市場的主流架構是 **SMP (Symmetric Multiprocessing, 對稱式多處理)**：
* **特徵**：眾生平等。每一個核心都可以執行作業系統核心函數與一般使用者程式。
* **物理結構 (Figure 1.8)**：每個 CPU 擁有自己私有的暫存器 (Registers) 與區域快取 (Local cache)，但所有 CPU 都必須透過**系統匯流排 (System bus)** 來存取同一塊**共享實體記憶體 (Physical memory)**。

### 3. 走向 Multicore：功耗與快取階層 (Cache Hierarchy)
![image](https://hackmd.io/_uploads/rkXbPUrhWl.png)
現代 SMP 系統幾乎都是 **Multicore (多核心)** 架構。相較於在主機板上插滿單核心晶片，將多個 Core 塞進同一張晶片有兩大物理優勢：
1. **通訊極快**：晶片內通訊 (On-chip communication) 的物理距離極短。
2. **功耗極低**：這對行動裝置 (Mobile devices) 與筆記型電腦而言是生死攸關的指標。

* **快取階層設計 (Figure 1.9)**：現代多核心晶片通常採用分層快取。每個 Core 擁有極度私有且快速的 **L1 Cache (Level 1 cache)**；而同一晶片上的多個 Core 則共同使用一個較大但稍慢的 **L2 Cache (Level 2 cache)** 來交換熱資料。

### 4. 突破極限的 NUMA 架構 (Non-Uniform Memory Access)
![image](https://hackmd.io/_uploads/S1ImPIrh-g.png)
當伺服器等級的系統試圖裝上數十甚至數百個核心時，SMP 架構會迎來毀滅性的瓶頸：**所有的核心都在搶同一條 System Bus 來讀寫記憶體，導致嚴重的塞車**。

為了解決這個瓶頸，硬體架構師發明了 **NUMA (非均勻記憶體存取)** 架構 (Figure 1.10)：
* **物理結構**：不再把所有記憶體丟在一起。而是給每一顆實體 Processor 配發一塊專屬的**區域記憶體 (Local memory)**。各個 Processor 之間再透過極高速的**系統互連通道 (Shared system interconnect)** 串聯，形成一個巨大的共享定址空間。

* **優勢**：完美的擴充性 (Scalability)。CPU 存取自己的 Local memory 時，完全不需要跟別人搶匯流排，速度極快。

* **致命代價 (NUMA Penalty)**：存取速度不再均勻 (Non-uniform)。如果 $CPU_0$ 需要讀取存在 $Memory_3$ 裡面的資料，就必須跨越互連通道去「遠端存取 (Remote access)」，這會帶來嚴重的**延遲懲罰 (Latency penalty)**。

## 叢集系統理論與架構深度剖析

在理解了單機內部的多處理器 (Multiprocessor) 架構後，1.3.3 節將視野擴大到了「跨實體主機」的系統串聯。

### 1. 鬆散耦合的巨獸：Clustered Systems (叢集系統)
![image](https://hackmd.io/_uploads/r1WS6FrhZx.png)
* **架構物理定義 (Figure 1.11)**：與上一節的 SMP（緊密插在同一張主機板上）不同，叢集系統是由兩台以上「完全獨立的電腦 (Nodes)」組合而成。這些電腦各自擁有 CPU 與記憶體，透過區域網路 (LAN) 或極高速的互連通道（如 InfiniBand）溝通，並共同連接到一個巨大的底層硬碟庫，稱為 **Storage-Area Network (SAN, 儲存區域網路)**。
* **Loosely Coupled (鬆散耦合)**：因為節點之間是透過網路線溝通，而非主機板匯流排，通訊延遲較高，故稱為鬆散耦合。

### 2. 生存的終極防線：High-Availability (高可用性)
叢集系統最主要的商業用途，是防止硬體損壞導致服務斷線。
* **Fault Tolerant (容錯能力)**：系統具備偵測、診斷並在單一元件損壞時持續運作的能力。
* **Graceful Degradation (優雅降級)**：當叢集內有 10 台伺服器，其中 2 台燒毀時，系統不會全面崩潰，而是將算力與服務品質按比例下降（剩下 80% 的效能），持續為客戶端提供服務。

### 3. 兩種熱備援架構：Asymmetric vs. Symmetric
叢集軟體 (Cluster software) 會在各個節點上運行，並透過網路不斷「監聽 (Monitor)」彼此的心跳。依照分工模式可分為：
* **Asymmetric Clustering (非對稱叢集)**：一台機器負責全職執行應用程式，另一台則處於 **Hot-standby mode (熱待機模式)**。待機機器唯一的任務就是緊盯著主機，一旦主機斷線，待機機器會瞬間接管 SAN 的控制權並重啟應用程式。
* **Symmetric Clustering (對稱叢集)**：所有機器「同時」執行應用程式，並互相監聽。這種架構能榨乾所有可用的硬體效能，但前提是應用程式本身必須支援多節點同時執行。

### 4. 算力與資料的雙面刃：HPC, Parallelization 與 DLM
叢集架構除了防護，也能用來發動算力海嘯：
* **High-Performance Computing (HPC, 高效能運算)**：將龐大任務（如天氣預報、大型語言模型訓練）分散給叢集內所有節點。這要求軟體工程師必須將演算法進行 **Parallelization (平行化)**，把程式碼拆解成能獨立在不同電腦上平行運算的碎塊。
* **資料庫災難防護 (Distributed Lock Manager)**：
  當叢集採用 Parallel clusters (平行叢集) 架構時，多台獨立的主機會試圖「同時」存取 SAN 上的同一份資料庫。
  由於一般作業系統根本不知道網路另一端有其他電腦在寫入硬碟，這會導致毀滅性的資料覆寫 (Data corruption)。因此，這類架構（如 Oracle 資料庫叢集）必須強制引入 **Distributed Lock Manager (DLM, 分散式鎖定管理員)**，透過極度複雜的網路協定來管理「誰當下有資格寫入硬碟」，確保不發生衝突操作。

## 雙重模式與系統防護架構剖析
### 1. 系統毀滅的物理防護網：Mode Bit
若讓所有的應用程式都能毫無限制地操控實體硬體，只要一行寫錯的記憶體指標程式碼，就能瞬間將整顆硬碟的資料抹除。為確保系統穩定，硬體架構師在 CPU 內部引入了一個極度關鍵的暫存器位元：**Mode bit (模式位元)**。

* **User Mode (使用者模式 / Mode bit = 1)**：
  這是一個「被閹割」的受限執行環境。一般應用程式（如瀏覽器、文字編輯器）平時都在此模式下運行。
* **Kernel Mode (核心模式 / Mode bit = 0)**：
  又被稱為 Supervisor mode 或 Privileged mode。在此模式下，CPU 擁有實體硬體的**絕對控制權**。作業系統的底層核心 (Kernel) 永遠在此模式下運行。

### 2. 權力的絕對界線：Privileged Instructions (特權指令)
為了落實這兩套模式的隔離，硬體設計規定了一系列 **特權指令**。
* **涵蓋範圍**：包含 I/O 設備控制、計時器 (Timer) 管理、中斷 (Interrupt) 管理等。
* **硬體防禦機制**：若一個在 User Mode 運行的程式，膽敢嘗試去執行特權指令（例如直接下達指令重啟主機板），CPU 硬體會**直接拒絕執行**，並將其視為非法操作 (Illegal instruction)。此舉會觸發一個 **Trap (陷阱 / 內部中斷)**，強行將控制權交還給作業系統，OS 通常會直接把這個違規的程式強制終止 (Terminate) 並傾印記憶體 (Memory dump)。

### 3. 合法的越界管道：System Call (系統呼叫 / Figure 1.13)
![image](https://hackmd.io/_uploads/ryOqvcHhWx.png)
既然 User Mode 的程式沒有權力操作硬體，那應用程式要如何讀取檔案或連上網路？答案是必須「委託」作業系統代勞。這個委託的動作，就是 **System Call**。

觀察課本 Figure 1.13 的狀態流轉，這是極度經典的考題動態過程：
1. **觸發 (Invoke)**：User Process 呼叫 System Call（例如 `read()` 檔案）。
2. **切換 (Trap to Kernel)**：硬體將其視為軟體中斷 (Software interrupt)，自動將 **Mode bit 從 1 切換為 0**，並將控制權跳轉至 OS 內部的中斷向量表 (Interrupt vector) 對應的服務常式。
3. **執行與驗證 (Execute & Verify)**：OS 在 Kernel Mode 下，嚴格檢查 User Process 傳遞進來的參數是否合法（避免惡意指標）。確認安全後，OS 代為操作硬體。
4. **返回 (Return)**：OS 完成任務，準備交還控制權。硬體將 **Mode bit 從 0 設回 1**，系統回到 User Mode，應用程式繼續往下執行。

### 4. 架構的現代擴充 (Multimode)
現代硬體架構已經超越了單純的 0 與 1。例如：
* **Intel 處理器**：設計了 4 個 Protection rings (環)。Ring 0 是 Kernel，Ring 3 是 User。
* **虛擬化技術**：引入了專屬的 **VMM (Virtual Machine Manager)** 模式，其權限介於一般的 User Process 與底層硬體的 Kernel 之間，用以管理多個虛擬作業系統。

## 虛擬化理論與架構深度剖析

#### 1. 虛擬化的本質：硬體抽象化 (Hardware Abstraction)
傳統上，一個作業系統會直接霸佔所有的 CPU、記憶體與硬碟。
虛擬化技術的出現，是為了在軟體層面創造出一種「幻覺 (Illusion)」。它將底層的實體硬體切分、抽象化，讓上層的每一個執行環境，都誤以為自己擁有一台完整且私有的實體電腦。這些環境被稱為 **Virtual Machines (虛擬機)**。透過這項技術，Windows 與 Linux 可以同時在一台實體主機上運行，且彼此互不干擾。

#### 2. 效能的生死分界：Emulation (模擬) vs. Virtualization (虛擬化)
這是考試與實務中最常混淆的兩個概念，其底層物理運作邏輯完全不同：
* **Emulation (模擬)**：
    * **情境**：當「來源程式碼的 CPU 架構」與「實際執行的實體 CPU 架構」**不同**時使用。例如早期 Apple 電腦從 IBM Power CPU 轉換到 Intel x86 CPU 時，推出的 "Rosetta" 翻譯技術。
    * **效能代價**：極度昂貴 (Heavy price)。因為每一行機器語言指令，都必須透過軟體「即時翻譯」成另一種架構的指令。這會導致程式執行速度出現斷崖式的暴跌。
* **Virtualization (虛擬化)**：
    * **情境**：客端作業系統 (Guest OS) 與底層實體 CPU 的架構是**相同**的（例如在 Intel x86 的主機上，跑 x86 版本的 Windows 虛擬機）。
    * **效能優勢**：因為指令不需要翻譯，可以直接丟給底層實體 CPU 進行原生執行 (Natively compiled)，因此效能耗損極低，幾乎逼近實體機的運行速度。

#### 3. 系統權力架構：Host, Guest 與 VMM (參考 Figure 1.16)
![image](https://hackmd.io/_uploads/SJjhzqP3Zx.png)
要達成虛擬化，系統架構中必須引入一個全新的特權階層：
* **Host Operating System (主端作業系統)**：安裝在實體硬體上的最底層 OS。
* **Guest Operating System (客端作業系統)**：安裝在虛擬機內部、被隔離起來的 OS。
* **VMM (Virtual Machine Manager / 虛擬機管理員)**：這是虛擬化架構的心臟（有時也被稱為 Hypervisor）。它負責運行 Guest OS、分配實體資源，並像防火牆一樣防止各個 Guest 互相越界破壞。
    * **現代架構演進**：在企業級的資料中心裡（如 VMware ESX 或 Citrix XenServer），VMM 甚至不需要依附在 Host OS 之上。**VMM 本身就是直接安裝在硬體上的底層作業系統**，藉此榨出最極致的硬體效能。

#### 4. 圖片說明
在 Figure 1.16 (b) 的右圖中，最關鍵的細節在於它畫了 三個獨立的 Kernel 框框。這代表的不是把一個作業系統核心切分給三個人用；相反地，是 「**這台實體電腦上，同時跑著三個完全獨立、互不相干的作業系統核心**」。

##### 1. 底層：Hardware (實體硬體)
這台電腦只有一顆實體 CPU（可能有很多核心）、一條實體記憶體（例如 32GB RAM）和一顆實體硬碟。

##### 2. 中間層：Virtual Machine Manager (VMM / 虛擬機管理員)
VMM 是整套虛擬化系統的核心樞紐。它的主要工作，是將底層的 32GB 實體記憶體與 CPU 算力進行抽象化與動態劃分，藉此為上層的多個客端系統 (Guest OS) 營造出獨佔實體硬體的幻覺。同時，VMM 負責攔截所有上層的硬體請求，並進行統一的排程與映射。

##### 3. 頂層：VM1 ~ VM3 (Virtual Machines / 虛擬機)
VM (Virtual Machine) 就是指「虛擬機」。VM1、VM2、VM3 就像是存在於軟體層面的三台「虛擬電腦」。
* **獨立的 Kernel：** 因為它們是三台獨立的電腦，所以它們各自必須安裝自己的作業系統。例如：
    * **VM1** 可能是安裝了 Windows 11，裡面跑著 Windows 的 Kernel。
    * **VM2** 可能是安裝了 Ubuntu Linux，裡面跑著 Linux Kernel (就像你現在用的 WSL2)。
    * **VM3** 可能是安裝了 Red Hat 伺服器，跑著另一個 Linux Kernel。

* **絕對的物理隔離 (Isolation)**：
    * 如果 VM1 裡面的 Windows 因為中了病毒，導致它的 Kernel 發生藍白當機 (Kernel Panic) 徹底死機，**VM2 和 VM3 完全不會有感覺**。因為崩潰的只有 VM1 自己的虛擬 Kernel，底層的 VMM 和實體硬體依然安然無恙。

##### 4. 那什麼才是「一個 Kernel 切成很多份」？
問題中提到的「把一個 Kernel 切分給很多人用」，這其實是另一種極度強大的現代技術，叫做 「容器化 (Containerization)」（最著名的代表就是 Docker）。

在 Docker 的架構中，就沒有 VMM，也沒有 VM1~VM3。所有的應用程式 (Processes) 都是直接跑在最底層唯一的 Host OS Kernel 上面。作業系統只是單純用「命名空間 (Namespaces)」的軟體魔法，把它們的視野蒙蔽起來，讓它們「以為」自己是獨立的。

## Kernel Data Structures
在開發底層系統（如微型作業系統 C 語言實作）時，最常面臨的抉擇就是如何儲存動態產生的任務。課本 1.9.1 節介紹了最基礎的三大類別：
#### 1. 從 Array (陣列) 到 Linked List (鏈結串列)
* **Array (陣列)：**
    * 這是最簡單的結構，主記憶體 (Main memory) 本身在硬體層面就是一個巨大的陣列。其優勢在於可以直接透過位址計算來進行「隨機存取 (Random Access)」。
    * **致命傷：** 當需要儲存大小未知、隨時會暴增或減少的系統資源時，陣列會面臨嚴重的記憶體搬移成本（插入/刪除極慢）。
* **Linked List (鏈結串列)：**
    * 為了解決陣列的痛點而生。它由不連續的記憶體區塊（節點）組成，透過「指標 (Pointers)」將彼此串接起來。
    * **優勢：** 大小極度彈性，且插入與刪除節點的效能極佳。
    * **劣勢：** 要找尋特定的第 $n$ 個元素，必須從頭開始遍歷 (Traversing)，時間複雜度為線性時間 $O(n)$。

#### 2. Linked List 的三大變體
針對不同的系統需求，鏈結串列衍伸出三種型態（需熟記中英對照與物理結構）：
![image](https://hackmd.io/_uploads/HyoFi9v3-x.png)
![image](https://hackmd.io/_uploads/rJ-co9whbx.png)
![image](https://hackmd.io/_uploads/ByP9s9v2Zx.png)
* **Singly linked list (單向鏈結串列)：**
    * 每個節點只有一個指標，指向下一個繼承者 (Successor)。
* **Doubly linked list (雙向鏈結串列 / Figure 1.18)：**
    * 每個節點擁有兩個指標，分別指向前驅者 (Predecessor) 與繼承者 (Successor)。這是 OS 核心中最常使用的結構，因為它允許雙向快速走訪。
* **Circularly linked list (環狀鏈結串列 / Figure 1.19)：**
    * 最後一個節點的指標不指向空值 (Null)，而是繞一圈指向「第一個節點」。這在實作 **Round-Robin (RR)** 排程演算法時是絕對的標準配備。

#### 3. Stack (堆疊)：系統呼叫的記憶體守護者
* **核心原則：** LIFO (Last In, First Out / 後進先出)。最後放進去的資料，必須最先被拿出來。
* **專屬操作：** 將資料放入稱為 Push (推入/壓入)；將資料取出稱為 Pop (彈出/取出)。
* **OS 底層應用：** 當系統在執行 C/C++ 程式並觸發 Function calls (函式呼叫) 時，作業系統會利用 Stack 來儲存三樣極度重要的東西：參數 (Parameters)、區域變數 (Local variables) 以及 返回位址 (Return address)。當函式執行完畢，系統會連續執行 Pop，精準回到原本的執行中斷點。

#### 4. Queue (佇列)：公平排程的基石
* **核心原則：** FIFO (First In, First Out / 先進先出)。如同在超市排隊結帳，先進入佇列的任務，先獲得處理資源。
* **OS 底層應用：** 在系統層級無處不在。例如送往印表機的列印任務 (Printer jobs)，或者是我們在第五章深究過的，所有等待被 CPU 執行的執行緒，都會被組織在 **Ready Queue (就緒佇列)** 之中。

## 為甚麼現代作業系統不用Array?
### 1. 痛點一：排程器根本不需要「隨機存取」
在 Ready Queue 中，排程器 (Scheduler) 幾乎從來不會下達這種指令：「請給我佇列裡的『第 57 個』任務」。
排程器的動作通常只有兩種：
* **Dequeue**：把佇列「最前面」的任務拿出來丟給 CPU。
* **Enqueue**：把新任務排到「最後面」，或依照優先權安插到「某個位置」。
既然不需要「找第 $n$ 個」，Array 最強大的 $O(1)$ 隨機存取優勢，在 OS 排程中形同英雄無用武之地。

### 2. 痛點二：任務中途拔除的「雪崩式搬移」($O(n)$ 災難)
這是陣列在 OS 中被判死刑的主因。
假設系統中有 10,000 個 Process 正在 Ready Queue 裡面排隊：
* **Array 的災難**：如果排在第 2 名的任務突然因為收到中斷訊號（例如被使用者按下 Ctrl+C 終止，或等待 I/O 被踢出），必須立刻從佇列中「拔除」。在陣列中，為了填補第 2 名的空缺，作業系統必須把後面 9,998 個任務的資料**全部往前搬移一格**。這種海量的 Memory Copy 對 CPU 來說是極度嚴重的純耗損 (Overhead)。
* **Doubly Linked List 的魔法**：如果是雙向鏈結串列，不管任務排在哪裡，只要修改它前後節點的指標 (Pointers)：`node->prev->next = node->next`，短短幾行機器語言指令，**$O(1)$ 瞬間完成拔除**，完全不需要搬移任何其他任務。

### 3. 痛點三：實體記憶體的「連續空間」要求
* **Array 的物理限制**：陣列要求在實體記憶體中必須是「絕對連續」的區塊。如果 OS 要建立一個能容納 10,000 個任務的陣列，它必須在 RAM 中找到一塊非常巨大的連續空地。在運作已久的系統中，記憶體早就碎裂化了，很難找到這麼大的連續空間。
* **Linked List 的彈性**：鏈結串列的節點可以散落在實體記憶體的「任何角落」。這讓 OS 在動態建立與銷毀 Process (如 `fork()`) 時，記憶體配置變得極度彈性且無壓力。

---

**【系統架構結論】**

你點出了一個軟體工程中非常經典的 **Trade-off (權衡)**：
* **Array** = 犧牲「新增/刪除」的效能，換取極致的「搜尋/讀取」速度。
* **Linked List** = 犧牲「搜尋/讀取」的效能，換取極致的「新增/刪除」速度與空間彈性。

因為作業系統的 Process 管理是一個**「瘋狂創建、瘋狂插隊、瘋狂刪除」**的動態地獄，所以 Linux 的核心結構 `task_struct` 最終選擇了 Doubly Linked List 作為串接所有任務的骨幹。

## 樹狀資料結構理論

這段內容正式宣告資料結構從「線性 (Linear)」跨入「階層式 (Hierarchical)」。在作業系統底層，當需要管理數以萬計且需要頻繁「搜尋、插入、刪除」的資源時（例如 CPU 排程器挑選下一個任務），Linked List 的 $O(n)$ 搜尋速度會成為嚴重的系統瓶頸。Tree 就是為了解決這個瓶頸而生的。

#### 1. 中英對照辭典 (Terminology Table)
針對考試要求，以下嚴格列出本節必須熟記的中英對照專有名詞：

| 英文專有名詞 (English) | 中文翻譯 (Chinese) | 核心定義與特徵 |
| :--- | :--- | :--- |
| **Tree** | 樹 | 表示階層關係的資料結構，節點間透過父子關係連結。 |
| **General tree** | 一般樹 | 一個父節點可以擁有「無限制數量 (Unlimited number)」的子節點。 |
| **Binary tree** | 二元樹 | 一個父節點「最多只能有兩個 (At most two)」子節點。 |
| **Left child / Right child** | 左子節點 / 右子節點 | 二元樹中，位於父節點左側與右側的子節點。 |
| **Binary search tree (BST)** | 二元搜尋樹 | 加上了**排序限制**的二元樹，規則為：`left_child <= parent <= right_child`。 |
| **Balanced binary search tree** | 平衡二元搜尋樹 | 透過演算法自我調整，確保整棵樹的深度不超過 $\log n$ 層，保證搜尋效能。 |
| **Red-black tree** | 紅黑樹 | 平衡二元搜尋樹的一種經典實作。**Linux 核心的 CPU 排程器 (CFS) 廣泛使用此結構。** |

#### 2. 二元搜尋樹 (BST) 的運作邏輯與 $O(n)$ 陷阱
觀察課本 Figure 1.20 的圖例，這是一棵標準的 BST。
如果系統要搜尋數字 `14`，演算法的視角如下：
1. 從根節點 `17` 開始比對：`14 < 17`，所以往左邊找。
2. 來到 `12`：`14 > 12`，所以往右邊找。
3. 找到 `14`。
每次比對都能直接淘汰掉一半的資料，這就是為什麼 BST 在理想狀態下，搜尋的時間複雜度是極快的 $O(\log n)$。

**為何最壞情況是 $O(n)$？**
課本特別括號註明 `(consider how this can occur)`，這是極度經典的考題。
如果今天系統依序插入五個任務，其優先權數值剛好是**已經排好序**的：`1, 2, 3, 4, 5`。
按照 BST 的規則：
* 插入 `1` (根節點)
* 插入 `2` (`2 > 1`，變成 `1` 的右子節點)
* 插入 `3` (`3 > 2`，變成 `2` 的右子節點)...以此類推。
整棵樹會變成一直線往右下角長，**在物理結構上，這棵 BST 已經退化成了一條「單向鏈結串列 (Singly Linked List)」**。此時若要搜尋 `5`，必須從頭走到尾，效能瞬間崩盤，退化成災難級的線性時間 $O(n)$。

#### 3. 作業系統的救贖：平衡二元搜尋樹
為了解決上述的退化危機，計算機科學家發明了 **Balanced binary search tree (平衡二元搜尋樹)**。
這種樹在每次插入新節點時，會檢查左右兩邊的分支是否「頭重腳輕」。如果發現樹快要變成一直線了，它會執行「旋轉 (Rotation)」操作，強行把樹的結構壓扁、拉平。
* **物理保證**：無論數值輸入的順序多麼極端，包含 $n$ 個項目的平衡樹，其最大層數絕對被壓制在大約 $\log_2 n$ 層以內。這在數學上給予了作業系統極度強大的效能保證：**無論系統有多繁忙，排程器找出下一個任務的時間，最差最差也只需要 $O(\log n)$。**

![image](https://hackmd.io/_uploads/BJ_tC5w2bx.png)

---

**【暫停點與系統架構思考】**

從 Array、$O(n)$ 的 Linked List，一路進化到能保證 $O(\log n)$ 的 Balanced BST（如紅黑樹），這展現了軟體工程中對於「搜尋」與「插入」效能的極致追求。

**架構思考**：
回顧第五章的內容，Linux 的 CFS (Completely Fair Scheduler, 完全公平排程器) 捨棄了傳統的 Multiple Queues (多重佇列)，改用 **Red-black tree (紅黑樹)** 來存放所有等待 CPU 的 Process。CFS 會將 Process 的 `vruntime` (虛擬執行時間) 作為樹的排序鍵值 (Key)。
結合本節所學的 BST 規則（左邊小、右邊大），當 CFS 排程器需要挑選「系統中當下最飢餓、`vruntime` 最小」的任務來執行時，它應該直接去這棵紅黑樹的**哪一個極端物理位置**去拔取節點？這種資料結構的選擇，為 OS 帶來了什麼決定性的優勢？

**重點摘要**
* **定義**：紅黑樹是一種「自平衡」的二元搜尋樹，透過替節點著色（紅或黑）並遵守特定規則來維持樹的高度。
* **優點**：確保搜尋、插入與刪除的最壞情況時間複雜度皆為 $O(\log n)$。
* **實務應用**：Linux 的 CFS 排程器利用紅黑樹快速找到虛擬執行時間（vruntime）最小的任務，這在頻繁變動的系統中效能極佳。

## 紅黑樹的底層邏輯與優勢剖析

這是一個在作業系統核心中極為迷人的設計。如果說普通的二元搜尋樹（BST）是一個「不穩定的天平」，那麼紅黑樹就是一個「會自我修正的智慧天平」。

#### 1. 什麼是紅黑樹？(The "Red-Black" Rules)
紅黑樹在每個節點上增加了一個儲存位元，用來表示節點的顏色。為了保證這棵樹「大致上是平衡的」，它必須嚴格遵守五大物理規則：
1. **節點非紅即黑**。
2. **根節點（Root）必為黑色**。
3. **葉節點（NIL，空節點）必為黑色**。
4. **紅節點的子節點必為黑色**（意即：不允許連續出現兩個紅色節點）。
5. **從任一節點到其所有葉節點的路徑，包含的黑色節點數量必須相同**。

#### 2. 為什麼要使用紅黑樹？(The "Why")
在資料結構的選擇上，系統架構師總是在「查詢速度」與「修改代價」之間做權衡：

* **對比普通 BST**：
  普通 BST 遇到排序好的資料會退化成 $O(n)$（像鏈結串列）。紅黑樹則保證了最長路徑不會超過最短路徑的兩倍，將搜尋效能鎖定在 $O(\log n)$。
* **對比 AVL 樹 (高度平衡樹)**：
  AVL 樹要求更嚴格的平衡，搜尋速度極快。但代價是每次「插入」或「刪除」時，可能需要進行多次旋轉來維持平衡。
  **紅黑樹的哲學**是「不追求完美的平衡，但追求更快的修改速度」。在需要頻繁安插與移除任務的 Linux 排程器中，紅黑樹的綜合效能（插入/刪除的負擔較小）優於 AVL 樹。

#### 3. Linux CFS 排程器的實體應用
在 CFS 中，所有等待被 CPU 執行的任務都被掛在一棵紅黑樹上。
* **排序依據**：任務的 `vruntime` (虛擬執行時間)。
* **搜尋邏輯**：越往樹的「左邊」走，`vruntime` 就越小，代表該任務越「飢餓」。
* **動作過程**：排程器只需要走到樹的「最左端節點」，就能在 $O(1)$ 或 $O(\log n)$ 內找到下一個該執行的任務。執行完後，更新時間並重新塞回樹中，紅黑樹會自動調整位置。

## 雜湊資料結構理論

在系統底層，若需要以最快速度透過「特定名稱」尋找「對應資料」（例如：透過檔案名稱尋找硬碟磁區位置），即使是時間複雜度為 $O(\log n)$ 的平衡樹仍可能不夠快。此時，系統會動用終極的資料結構：雜湊。

#### 1. 必考中英對照辭典 (Terminology Table)

| 英文專有名詞 | 中文翻譯 | 核心定義與特徵 |
| :--- | :--- | :--- |
| **Hash function** | 雜湊函式 | 接收資料輸入，執行數學運算後，吐出一個在固定範圍內的數值（作為陣列索引）。 |
| **Hash map** | 雜湊對應表 | 儲存 `[key:value]` (鍵與值) 配對的資料結構。 |
| **Hash collision** | 雜湊碰撞 | 兩個不同的輸入資料，經過數學運算後，得到完全相同的輸出索引值。 |

#### 2. $O(1)$ 的魔法：雜湊運作邏輯
![image](https://hackmd.io/_uploads/Byt9vjvn-l.png)
根據 Figure 1.21，雜湊對應表的底層骨幹其實就是一個**陣列 (Array)**。
完美的存取流程如下：
1. **輸入鍵值 (Key)**：例如使用者名稱 "UserA"。
2. **數學轉換**：`hash_function("UserA")` 透過數學公式（如字元 ASCII 碼加總後取餘數），計算出一個整數，例如 `3`。
3. **陣列存取**：直接前往底層陣列的索引 `[3]`，獲取對應的資料 (Value)，例如記憶體位址或密碼。
由於陣列具備絕對的 $O(1)$ 隨機存取特性，因此不論系統中註冊了十筆還是十億筆資料，計算與尋找的時間永遠是極短的常數級別。

#### 3. 物理缺陷與解法：雜湊碰撞 (Hash Collision)
數學上存在一個必然現象：當輸入的可能性（無限多種字串）大於陣列的大小（有限的記憶體空間）時，必定會發生**雜湊碰撞**。例如 "UserA" 與 "UserB" 經過公式計算後，剛好都得到索引 `3`。

* **標準解法 (Chaining)**：當發生碰撞時，系統會在陣列的索引 `[3]` 位置，掛載一條 1.9.1 節學過的**鏈結串列 (Linked List)**。後來的 "UserB" 資料會被當作一個新節點，串接在 "UserA" 資料的後方。
* **效能退化**：如果雜湊函式設計不良（分配不均勻），導致大量資料全部撞在同一個索引上，該格子底下的鏈結串列會變得極度冗長。此時若要尋找資料，必須順著鏈結串列一個一個比對，時間複雜度將會從最速的 $O(1)$ 垂直退化回鏈結串列的 $O(n)$。

## Bitmap 空間壓縮理論

當作業系統需要管理極度龐大、且狀態只有「有/無」兩種情況的實體資源時，若採用傳統的陣列或鏈結串列，會浪費極多無謂的記憶體空間。Bitmap 就是為了解決「空間效率 (Space efficiency)」而生的終極武器。

#### 1. 必考中英對照辭典 (Terminology Table)

| 英文專有名詞 | 中文翻譯 | 核心定義與特徵 |
| :--- | :--- | :--- |
| **Bitmap / Bit vector** | 位元圖 / 位元向量 | 由一連串的二進位數字 (0 與 1) 組成的字串，用以表示資源的狀態。 |
| **Disk block** | 磁碟區塊 | 實體硬碟儲存資料的最小切分單位。作業系統極度仰賴 Bitmap 來管理這些區塊。 |
| **Space efficiency** | 空間效率 | 資料結構佔用記憶體多寡的指標。Bitmap 是空間效率極高的代表。 |

#### 2. Bitmap 的物理對應與運作邏輯
Bitmap 的核心精神是：**讓資料結構中的第 $i$ 個位元，精準對應到系統中的第 $i$ 個實體資源。**

以課本的字串為例：`001011101`
若定義 `0` 代表資源「可用 (Available)」，`1` 代表「已被佔用 (Unavailable)」，從最左邊（第 0 號位元）開始解讀：
* 第 0, 1 號位元為 `0` $\rightarrow$ 資源 0, 1 可用。
* 第 2 號位元為 `1` $\rightarrow$ 資源 2 已被佔用。
* 最終系統可以極速判定：資源 2, 4, 5, 6, 8 處於忙碌/佔用狀態；資源 0, 1, 3, 7 處於空閒狀態。

#### 3. 為什麼不直接用布林陣列 (Boolean Array)？
這是一個非常經典的系統底層設計問題。
在多數高階程式語言（如 C/C++）中，宣告一個 `bool` 變數（即 `true` 或 `false`），編譯器為了符合 CPU 的記憶體定址規則，通常會直接分配 **1 個 Byte (即 8 個 Bits)** 的空間給它。

* **如果管理 8,000 個磁碟區塊**：
    * 用 Boolean Array：需要 8,000 Bytes 的記憶體。
    * 用 **Bitmap**：只需要將 8,000 個狀態塞進 8,000 個 Bits 裡，除以 8 之後，**總共只需 1,000 Bytes**。
在記憶體極度珍貴的作業系統核心（或嵌入式設備）中，這種直接省下 8 倍空間的設計，是提升效能的絕對關鍵。

#### 4. 補充：Linux 核心資料結構真實檔案 (Blue Box)
課本最後的藍色區塊強調，這些資料結構都實際躺在 Linux 的原始碼樹 (Source tree) 之中，這也是系統工程師必備的常識：
* **Linked List**: 放在 `<linux/list.h>`
* **Queue**: 實作為 `kfifo`，放在原始碼的 `kfifo.c`
* **Balanced BST**: 實作為紅黑樹，放在 `<linux/rbtree.h>`

## P2P 系統理論與通訊架構剖析

在探討完單機系統的 CPU 排程與記憶體資料結構後，1.10.4 節將視角拉遠，探討由多台獨立主機構成的分散式系統 (Distributed System) 的另一種極端型態：**P2P 運算 (Peer-to-Peer Computing)**。

#### 1. 消滅效能瓶頸：P2P 的物理優勢
在傳統的 Client-Server 架構中，伺服器是絕對的中心。當幾萬個客戶端同時要求下載檔案時，伺服器的網路頻寬與 CPU 算力會瞬間耗盡，形成嚴重的**瓶頸 (Bottleneck)**。

P2P 架構完美解決了這個問題。在 P2P 網路中，沒有絕對的提供者與消耗者。當一個節點下載了檔案的片段後，它會立刻轉變為「伺服器」，將該片段提供給其他正在下載的節點。**網路中參與的節點越多，整體的可用頻寬與服務能量反而越大**，這與傳統架構剛好完全相反。

#### 2. 必考重點：尋找服務的兩大協定
當一個新節點加入 P2P 網路時，它面臨的最大物理難題是：「我該去哪裡找我要的資料？」課本指出了兩種截然不同的解決方案：

* **策略一：Centralized Lookup Service (集中式查詢服務)**
    * **運作邏輯**：網路上依然存在一台「中心目錄伺服器」。所有節點上線時，必須先向這台伺服器「註冊」自己擁有什麼檔案。當節點要找檔案時，先向中心伺服器查詢擁有該檔案的節點 IP，隨後**略過中心伺服器，直接與目標節點建立點對點連線並傳輸資料**。
    * **歷史案例**：早期的 **Napster** 系統即採用此架構。
* **策略二：Discovery Protocol / Broadcasting (發現協定與廣播)**
    * **運作邏輯 (參考 Figure 1.23)**：這是一種純粹的去中心化 (Decentralized) 架構。沒有任何目錄伺服器。節點在網路上直接發出**廣播 (Broadcasting)**：「誰有檔案 X？」。所有收到廣播的相鄰節點若擁有該檔案，就會直接給予回應。
    * **歷史案例**：早期的 **Gnutella** 系統。

#### 3. 現代妥協：Hybrid (混合式) 與 VoIP
純廣播機制的網路風暴 (Broadcast storm) 容易導致區域網路癱瘓，且無法保證能找到檔案。因此，現代商業應用多半選擇妥協。

課本以 **Skype** 為例，它是一種提供 **VoIP (Voice over IP, 網路語音通話)** 的軟體。
Skype 採用了**混合式 (Hybrid)** 做法：
1.  使用者輸入帳號密碼登入時，連線至 Skype 的**集中式伺服器 (Centralized login server)** 進行身分驗證，並尋找聯絡人是否在線。
2.  一旦確認雙方都在線上並開始通話，影音封包就會**完全繞過伺服器，直接在兩個 Peers 之間進行 P2P 傳輸**，藉此省下驚人的伺服器維運成本與頻寬耗損。
