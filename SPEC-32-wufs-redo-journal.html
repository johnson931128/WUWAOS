Spec 32：WUFS0002 整磁區 redo journal 與安全儲存 ​

日期：2026-11-06。

狀態：WUFS0002、redo/recovery、舊版唯讀、主機映像安全更新已實作；scratch QEMU 已驗證正常寫入、錯誤回復、滿盤保護與 fan 儲存。未宣稱實體斷電或所有 VirtIO 硬體的 flush 語意均已驗證。

目標與範圍 ​

公開檔案系統修改操作必須在寫回正式磁區前完成一筆有界交易。遇到錯誤或容量不足時，尚未提交的修改只存在 RAM，不得將原檔或 metadata 部分改壞。已提交但尚未完整 checkpoint 的交易，重新開機時要重做完整紀錄。包含 mkdir、touch、remove、remove_tree、copy、整檔 write、truncate 與 FD inode write。

教科書中的 journaling／redo 與 recovery 概念參照使用者筆記 notes/chapter 14 File-System Implementation.md §14.7；區塊裝置請求及 DMA/I/O 分層參照 notes/ch12 I_O Systems.md。這裡是 WUWAOS 的整磁區 redo 設計，不是 ext3 或 POSIX VFS。

磁碟相容與布局 ​

  • WUFS0001 不做原地轉換，kernel 僅在嚴格 layout／metadata 驗證通過後唯讀掛載；所有修改回 -30（read-only）。host make_disk.py 對 V1 不更新映像；指定 --install 時拒絕，建立新檔案系統需指定新的 DISK_IMAGE。
  • 全零新磁碟由 kernel 或 host 工具建立 WUFS0002。不支援未知非空白映像自動格式化。
  • 16 MiB 映像固定配置如下；所有 LBA 單位均為 512 bytes。
LBA內容
0Superblock；沿用前 9 個 WUFS 幾何欄位，word 11–13 記錄 journal 起點、長度及容量
1Journal header，含 WUJNL002、版本、sector 數、commit state 及 CRC32
2–109-sector 目標 LBA 表，可列 1152 個 sector
11–11621152 個完整 512-byte redo sector image
1163Inode bitmap
1164–1171Block bitmap
1172–1191128 個、每個 80-byte 的 inode
1192 之後Data 區

Journal extent 總長 1162 sectors；其 sectors 在 block bitmap 中永久標為已用。Superblock layout 必須精確吻合該格式，超過 32768 sectors 的裝置拒絕掛載。Header 全零表示沒有 pending transaction；任何非零但無效的 header 都拒絕掛載，不猜測、不清除。有效紀錄需在 replay 前驗完 header state/reserved bytes、CRC、count、目標範圍、重複 LBA 及完整 payload；目標不得落在 superblock 或 journal。

Commit、錯誤與 recovery ​

一筆 transaction 將每個唯一目標 sector 暫存在 589,824-byte RAM buffer（另有 4.5 KiB LBA index），讀取會先查 staged copy。配置快取需連續 144 個 4 KiB 頁；失敗時不掛載新格式磁碟或拒絕 V2 掛載。最多 1152 個不同 sector；超過即回 -28，整筆 abort，正式區尚未寫入。

Commit 順序為：寫完整目標表與 redo payload → VirtIO FLUSH → 寫已提交 header → FLUSH → 將每個 redo sector 寫回 home LBA → FLUSH → 清零 header → FLUSH。FLUSH feature 未協商到時，乾淨的 V2 volume 只唯讀掛載；若 header pending，拒絕掛載而不嘗試不耐久的 replay。VirtIO block flush request 依 VirtIO 1.2 block FLUSH request 格式，sector 欄位設為 0。

此實作假設單 hart 核心交易期間不與另一個核心並行修改 WUFS，也不允許 host 工具在 QEMU 使用映像時同時改寫它。FLUSH 提供裝置所宣告的持久化屏障；若裝置回報寫入完成但未遵守該契約，軟體無法保證媒體持久性。Checksum 用來拒絕損毀紀錄，不是資料救援機制；任何 torn／損毀後的非零 header 都保留並拒絕掛載，不自動修復。

整檔 payload 也在 redo buffer 中，因此同一 transaction 可以在 staged bitmap 釋放舊 blocks 後再配置新 blocks；正式磁碟直到 commit 前仍保有完整舊版本。這讓 fs_write／fan 的單次整檔 SYS_FS_WRITE 原子發佈，不必同時保留舊檔和新檔的全部空間。Copy、刪除樹等操作超過 journal sector 上限時整筆拒絕，不分批留下半套樹。

Commit header 成功持久化後，即使後續 home write 回錯，呼叫者仍可能收到 -5，而重啟後 redo 會使操作生效；這是結果不確定狀態，使用者不應盲目重試。任何交易 I/O 失敗會將該次開機的 volume 標為 offline；重新啟動後由有效 committed log 決定 replay。區塊請求逾時仍沿用既有 fail-stop 行為，不會返回 syscall 錯誤；需要重啟後再復原。

FD 的每次 io_write 最多提交 512 bytes 為一個 transaction；多次 FD write 不合併成整檔 transaction。O_TRUNC 與後續 write 是分開的交易，因此 shell > file 在 open/truncate 成功後，後續寫入失敗不會還原舊內容。資料寫入可按 FD 呼叫粒度失敗；metadata 不得假裝成功。

驗證及 host formatter ​

Kernel 掛載前驗證 superblock 範圍與精確布局；replay 後掃描 inode/block bitmaps、inode 類型與大小、必要 data pointers、indirect pointers 範圍/重複/bitmap 所有權、directory entry 名稱和 inode 編號、root .／..、目錄可達性與父項。Data 區 bitmap 必須與 inode pointer ownership 相符。這是 WUFS 的一致性檢查，不包含資料內容 checksum，也不會自動修復壞格式。

tools/make_disk.py 只直接更新無 pending journal 且通過同等 WUFS0002 metadata 驗證的映像；任何非零 journal header（有效或損毀）都拒絕。工具在記憶體完成修改後，寫同目錄暫存檔、flush/fsync，再用 replace 取代目標；POSIX 也 fsync parent directory。Windows 對目錄項目持久性的保證受 OS／檔案系統限制。Pending journal 必須先由 kernel 開機復原後，再以正確流程處理映像；host 工具不做 replay。

build/kernel.elf 是 QEMU 實際啟動的 debug kernel。build/kernel-disk.elf 只是普通檔案系統副本；因 kernel ELF 超過每檔案 528384-byte 限制，該副本用 llvm-objcopy --strip-all 壓小，啟動方式不變。

新磁碟與 pending recovery 操作 ​

舊預設 build/wuwaos.img 若是 WUFS0001，會保留唯讀。建立並啟動一顆新 WUFS0002：

powershell
wsl -d Ubuntu -- bash -lc 'cd /mnt/c/programing/WUWAOS && make run DISK_IMAGE=build/wuwaos-v2.img SWAP_IMAGE=build/wuwaos-v2-swap.img'
1

portable Windows 環境可執行 .\Start-WUWAOS.cmd shell 進入 bundled Bash，再執行相同的 make run DISK_IMAGE=... SWAP_IMAGE=...。若 host formatter 因 pending journal 拒絕更新，先直接呼叫 QEMU，跳過 disk-image target；以下例子使用上述兩個檔名：

bash
qemu-system-riscv64 -machine virt -smp 1 -m 128M -nographic -bios default \
  -kernel build/kernel.elf -global virtio-mmio.force-legacy=false \
  -drive file=build/wuwaos-v2.img,if=none,format=raw,id=fs \
  -device virtio-blk-device,drive=fs \
  -drive file=build/wuwaos-v2-swap.img,if=none,format=raw,id=swap \
  -device virtio-blk-device,drive=swap

若要復原 make run-disk 的預設映像，在專案目錄先用 make 建置 build/kernel.elf。再執行上述直接開機指令，把 file=build/wuwaos-v2.img 換成 file=build/wuwaos-cli.img，並省略兩個 swap 參數。磁碟開機載入器會拒絕有待重播紀錄的映像，因此復原時要由 QEMU 直接載入核心。

核心掛載時先重播有效的已提交交易，再清除 header。退出 QEMU 後，就能以原本的指令重新啟動該映像。若 journal header 非零但無效，核心會拒絕掛載，應保留映像供檢查。

驗收紀錄 ​

2026-11-06，WSL Ubuntu／Clang／QEMU virt 單 hart、128 MiB。未加入測試程式碼；下列映像與 serial log 均在 build/wufs-*-scratch.*／build/qemu-*.log，未使用正常 WUFS 或 swap 磁碟。

  • make -j2 all build/kernel-disk.elf 通過 -Wall -Wextra -Werror 及既有 linker budget。新 V2 host image 為 16 MiB，magic/欄位與 journal LBA 範圍符合表格；主機 formatter 能在既有 V2 上驗證並原子更新。
  • 正常 QEMU 建立 /txn、整檔寫入 hello、touch、copy、cat、remove、remove-tree；echo >／>> 的 FD create/truncate/append 寫入成功，重啟後 cat /txn/a 仍讀到 hello。fan /home/user/note 輸入 fan safe save，Ctrl+O 顯示 14 bytes Saved，Ctrl+X 離開；重啟再開 fan 顯示同樣內容，cat 亦讀回。
  • 滿盤 scratch：host 安裝 409600-byte source、KEEP-OLD destination 及 29 個 528384-byte filler，剩 303 sectors。QEMU cp /home/user/source /home/user/dest 回 -28；隨後 cat 仍是 KEEP-OLD。關機後 host formatter 完整驗證同一磁碟成功，journal header 為零且 free sectors 仍為 303。
  • QEMU blkdebug 在 journal payload LBA 11 注入單次 EIO。對既有 destination 的整檔 write 回 -5；header 保持全零，host metadata 驗證成功，解析目的檔仍是原內容 NEW。紀錄：build/qemu-precommit.log。
  • QEMU blkdebug 在 home inode sector LBA 1178 注入 EIO，讓 LBA 1163 inode bitmap 已 checkpoint、後續 home sector 失敗。操作回 -5，磁碟保留有效 WUJNL002。普通 QEMU 重啟印出 Replayed committed WUFS journal，ls / 找到 /partial/，且 host 驗證/更新成功。紀錄：build/qemu-checkpoint.log、build/qemu-replay.log。
  • 另在 home inode bitmap LBA 1163 注入 EIO，單筆 mkdir 回錯，重啟 replay 後 /fault/ 存在。QEMU 的 blkdebug I/O error 測試是 checkpoint failure/restart recovery，不代表真實突然斷電測試。故障情境使用 werror=report,rerror=report 避免 QEMU 預設暫停 VM。
  • 全零 scratch 首次 boot 顯示 Initializing blank disk as WUFS0002，目錄可讀；關機後 host formatter 通過 metadata validation。最後一 byte 非零的 unknown scratch 顯示 Unknown or damaged filesystem ... refusing format，SHA-256 前後皆 0cc9ac108468572e9a13a9e41c02fe8d76efa9708f7f8a86a3b103a7dba21a64。
  • 無效非零 journal header scratch 的 kernel log 為 Invalid or unrecoverable journal，host formatter 明確拒絕；映像 SHA-256 前後皆 0109f2ac1eb3487dd801cee04d477ede114480a99f1ee679189b70bd250da5bb。將 data_start 改錯的 layout scratch 被 kernel、host 都拒絕且 hash不變；把 /home/user/dest inode direct pointer 改為 journal sector 1 的 scratch 被 kernel metadata validator、host validator 都拒絕且 hash 不變。紀錄：build/qemu-invalid-journal.log、build/qemu-invalid-layout.log、build/qemu-invalid-pointer.log。
  • 原 WUFS0001 磁碟的獨立 scratch copy 可唯讀掛載及 ls /；寫入回 -30。host tool 執行後 hash 不變。此 scratch copy SHA-256 與原映像皆為 6ba61b2e9e6c5af4931dd39d338619bf66bf25c5639bb916adc59b6b62fd4989；原始 build/wuwaos.img 未供 QEMU 掛載、未修改。QEMU 使用獨立 scratch swap。
  • 原始 swap build/wuwaos-swap.img 在驗收前後均為 SHA-256 f6ddb73f54cf434916200d752a0596b14da7d6534fe0f8cf454e6b1c02078355；QEMU 使用獨立 scratch swap。

限制 ​

  • Flush 信任裝置宣告的 VirtIO FLUSH 語意；QEMU 注入的 sector write errors 不等於電源中斷或實體裝置快取測試。資料區整體 checksum、磁碟影像本身的損毀救援、journal 自動修補均未實作。
  • 1152-sector capacity 是 hard bound；大量 remove_tree／copy 可能回 -28，呼叫者可用較小操作拆分，但每次 API 仍保持單筆 transaction。
  • Legacy V1 在 write-protect 協定中檢查後唯讀，不升級；不支援 FLUSH 的 V2 只在 journal clean 時唯讀可用。
  • DMA request timeout 仍停住核心；不做 device reset/retry。
