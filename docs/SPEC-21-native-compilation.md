# Spec 21：在 WUWAOS 中編譯與執行 C 程式的長期目標

## 需求與目標

使用者希望記錄：WUWAOS 以 C 開發，但現在系統本身沒有編譯器；未來希望能在 WUWAOS 內編輯 C 程式、編譯為 RISC-V 可執行檔，再從 shell 執行並取得結果。本文件是方向與依賴的規劃，不表示已開始實作，也不預先限定必須自行撰寫編譯器。

## 目前實際流程

Windows 主機透過 WSL Ubuntu 執行 `make`，由主機端 Clang 交叉編譯（在主機上產生目標 RISC-V 機器碼），並經連結器產生核心和使用者映像。QEMU 使用 `-kernel` 載入核心 ELF（可執行與連結格式）；shell、app、fan 映像則先在主機編譯，轉成 binary（機器碼資料）嵌入核心，核心依內建程式 ID 載入。

WUFS 中 `/boot/kernel.elf` 是磁碟副本，現階段不是開機載入來源。`fan` 可以編輯符合其容量及文字格式限制的 `.c` 檔，但沒有 WUWAOS 內的 C 編譯器、一般磁碟 ELF 載入器及執行外部檔案的命令。現有 `exec` 僅支援內建程式 ID，並非一般路徑執行。

## 所需能力與設計選項

1. **外部程式載入**：新增 ELF 載入器，驗證標頭、架構、程式段、邊界、權限、入口、記憶體配置及錯誤復原；設計從 WUFS 路徑執行以及參數傳遞。先支援範圍明確的 RV64 靜態執行檔，不承諾動態連結。
2. **檔案與行程介面**：依選用工具實際需求擴充檔案描述號、讀寫、位置、關閉、目錄、標準輸入輸出、錯誤及行程控制等介面；現有路徑式 WUFS 呼叫不能視為完整 POSIX。規格和資源限制待另案定義。
3. **執行環境與工具鏈**：提供程式啟動碼、函式庫、標頭及相容的 ABI（程式呼叫與資料格式約定），並評估移植現有編譯器或先使用範圍較小的工具。視工具的輸出格式，也可能需要組譯器及連結器；若選擇直接產生可執行檔的工具，流程可以不同。不要假設可不經移植就執行 Linux 編譯器。
4. **資源與檔案操作**：評估記憶體、swap、檔案容量、資料搬移與終端操作。現行 WUFS 單檔約 516 KiB，fan 文字上限 2048 bytes，這些限制可能影響編譯器與來源碼，需以實際選用工具重新評估。

## 建議階段與驗收方向

- 第一階段：主機交叉編譯一個簡單 RV64 程式，放入 WUFS，WUWAOS 從路徑載入並執行，正確處理正常結束與無效檔案。這是外部程式執行的基礎，還不是系統內編譯。
- 第二階段：釐清並補齊所選工具依賴的檔案／行程介面及使用者執行環境，建立可重現的來源碼、工具與產物放置方式。
- 第三階段：在 WUWAOS 內執行相容的編譯工具，把來源檔產生為可執行檔，再執行並觀察結果；錯誤訊息和失敗後資源回收也需驗收。

各階段的實際工具、支援範圍、細節、驗證方法與安全限制，應在開始該階段前另行規劃與討論。本次僅記錄規格並發布文件；尚未實作或在 QEMU 驗證上述新能力。
